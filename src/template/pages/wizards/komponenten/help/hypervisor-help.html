Hypervisor Name

Ein eindeutiger Name für Ihren Hypervisor oder Cluster.

Was ist ein Hypervisor?

Die Software, die virtuelle Maschinen (VMs) erstellt und verwaltet - quasi der "Manager" für alle virtuellen Server.

Warum Virtualisierung wichtig ist:

  • Bessere Hardware-Auslastung: Ein physischer Server kann 10-30 VMs hosten
  • Flexibilität: VMs schnell erstellen, verschieben, löschen
  • Kosteneinsparung: Weniger physische Server = weniger Strom, Kühlung, Platz
  • Hochverfügbarkeit: VMs können live zwischen Hosts verschoben werden

Namens-Beispiele:

  • "ESXi-Cluster-01" - VMware Cluster Nr. 1
  • "Hyper-V-Host-DC1" - Hyper-V im Datacenter 1
  • "Proxmox-Production" - Proxmox Produktiv-Umgebung
  • "vSphere-Healthcare" - VMware für Healthcare-Systeme
Ohne Virtualisierung bräuchten Sie für jede Anwendung einen eigenen Server!

Typ / Hersteller

Welche Virtualisierungs-Software wird verwendet?

Hypervisor-Kategorien:

  • VMware (Marktführer):
    • ESXi: Einzelner Host, kostenlose Version verfügbar
    • vSphere: Enterprise-Plattform mit vCenter (Cluster-Management)
    • Sehr stabil, teuer, größte Feature-Set
    • Gold-Standard im Krankenhaus
    • 90%+ der Krankenhäuser nutzen VMware!
  • Microsoft Hyper-V:
    • In Windows Server integriert
    • Gut für Windows-lastige Umgebungen
    • Günstiger als VMware
    • Failover Cluster für HA
  • Open Source:
    • KVM: Linux Kernel-basiert, sehr performant
    • Proxmox VE: KVM mit Web-UI, sehr beliebt für KMU
    • XenServer/XCP-ng: Citrix (kommerziell) / XCP-ng (Open Source)
    • OpenStack: Cloud-Plattform, komplex
    • Kostenlos, aber weniger Support
  • Cloud:
    • Azure: Hyper-V-basiert
    • AWS: Nitro Hypervisor (custom)
    • Google Cloud: KVM-basiert
    • Keine eigene Verwaltung nötig
  • Andere:
    • Oracle VM: Für Oracle-Datenbanken
    • Nutanix AHV: Teil der Nutanix HCI-Lösung

Typ 1 vs Typ 2 Hypervisor:

  • Typ 1 (Bare Metal): Läuft direkt auf Hardware (ESXi, Hyper-V) - Für Server!
  • Typ 2 (Hosted): Läuft auf OS (VirtualBox, VMware Workstation) - Für Desktop!
Wahl hängt ab von: Budget, Expertise, Ökosystem (Windows vs Linux)

Version

Die installierte Hypervisor-Version.

Warum Version kritisch ist:

  • Neue Hardware-Support (CPU, RAM, NVMe)
  • Performance-Verbesserungen
  • Sicherheits-Patches
  • Neue Features (z.B. vSphere 8: vGPU-Verbesserungen)
  • Kompatibilität mit VM-Hardware-Versionen

Beispiele:

  • "ESXi 8.0 U2" - VMware Version 8.0 Update 2
  • "Hyper-V 2022" - Windows Server 2022 Hyper-V
  • "Proxmox VE 8.1" - Proxmox Version 8.1

Update-Strategie:

  • Nicht neueste Version = fehlt Support für neue Hardware
  • Zu alte Version = Sicherheitsrisiko
  • Empfehlung: N-1 Version (eine zurück) = stabil + aktuell
Hypervisor MUSS aktuell gehalten werden - alte Versionen = Angriffspunkt!

Management IP / URL

Die Adresse zur Verwaltung des Hypervisors.

Management-Zugriff:

  • ESXi: Web-UI (https://esxi-host-ip) oder vCenter
  • vCenter: https://vcenter.example.com (zentral für Cluster)
  • Hyper-V: Hyper-V Manager oder System Center VMM
  • Proxmox: Web-UI (https://proxmox-ip:8006)

Best Practices:

  • Dediziertes Management-Netzwerk (VLAN)
  • Nur aus Admin-Netz erreichbar
  • MFA aktivieren (wo möglich)
  • Niemals direkt aus Internet!
Management-Zugriff ist kritisch - wenn kompromittiert, sind ALLE VMs gefährdet!

Cluster-Konfiguration

Laufen mehrere Hypervisor-Hosts zusammen als Cluster?

Was ist ein Cluster?

Mehrere physische Server, die als ein System arbeiten - VMs können zwischen ihnen verschoben werden.

Warum Cluster wichtig:

  • Hochverfügbarkeit (HA): VM startet automatisch auf anderem Host bei Ausfall
  • Live Migration: VM ohne Downtime verschieben (vMotion, Live Migration)
  • Load Balancing: Last automatisch verteilen (DRS)
  • Wartung ohne Downtime: Host in Wartungsmodus → VMs migrieren automatisch

Einzelner Host vs Cluster:

  • Einzelhost: Einfach, günstig, aber Single Point of Failure
  • Cluster: Teurer, komplexer, aber hochverfügbar
Für kritische Systeme (KIS, PACS): Cluster ist Pflicht!

Cluster Name

Der Name des Clusters (Gruppe von Hosts).

Namens-Beispiele:

  • "Production-Cluster" - Produktiv-VMs
  • "HA-Cluster-01" - HA-Cluster Nr. 1
  • "Test-Cluster" - Test-Umgebung
  • "Healthcare-Cluster" - Medizinische Systeme

Anzahl Hosts im Cluster

Wie viele physische Server sind im Cluster?

Typische Größen:

  • 2 Hosts: Minimum für HA, aber bei Wartung keine Redundanz mehr
  • 3 Hosts: Ideal - HA funktioniert auch bei Wartung eines Hosts
  • 4-8 Hosts: Standard für mittelgroße Umgebungen
  • 8+ Hosts: Große Rechenzentren

N+1 Redundanz:

Cluster muss auch funktionieren, wenn ein Host ausfällt oder in Wartung ist

Beispiel-Berechnung:

100 VMs, 4 Hosts → Jeder Host ~25 VMs → Bei Ausfall: 3 Hosts müssen 100 VMs tragen können → Jeder Host muss ~33 VMs schaffen
Minimum 3 Hosts empfohlen - sonst kein echtes HA!

HA (High Availability)

Automatischer Neustart von VMs bei Host-Ausfall.

Was ist HA?

Wenn ein Host ausfällt, werden dessen VMs automatisch auf anderen Hosts neu gestartet.

Wie HA funktioniert:

  1. Host fällt aus (Hardware-Defekt, Stromausfall)
  2. Cluster erkennt Ausfall (Heartbeat fehlt)
  3. VMs werden auf verbleibenden Hosts neu gestartet
  4. Dauert 1-5 Minuten (kurze Downtime)

HA vs Fault Tolerance:

  • HA: VM wird neu gestartet (kurze Downtime)
  • Fault Tolerance: VM läuft parallel auf 2 Hosts (keine Downtime, aber sehr ressourcen-intensiv)

Voraussetzungen:

  • Shared Storage (alle Hosts müssen auf gleiche VMDKs zugreifen können)
  • Genug freie Ressourcen auf anderen Hosts
HA aktivieren ist Best Practice für Produktiv-Cluster!

DRS / Load Balancing

Automatische Lastverteilung von VMs über Hosts.

Was ist DRS?

Distributed Resource Scheduler (VMware) - verschiebt VMs automatisch für optimale Auslastung.

Modi erklärt:

  • Fully Automated:
    • DRS verschiebt VMs automatisch
    • Keine manuelle Bestätigung
    • Beste Performance
    • Empfohlen für Produktion
  • Partially Automated:
    • DRS schlägt Verschiebungen vor
    • Admin muss bestätigen
    • Mehr Kontrolle
  • Manual:
    • Keine automatischen Verschiebungen
    • Nur Empfehlungen
    • Admin entscheidet alles
  • Disabled: DRS aus

Vorteile:

  • Verhindert, dass ein Host überlastet ist
  • Optimale Performance für alle VMs
  • Automatische Initial Placement (wo neue VM starten?)

Microsoft-Äquivalent:

Live Migration in Hyper-V (manuell oder gescriptet)
DRS ist "Luxus" aber sehr praktisch - spart viel manuelle Arbeit!

Storage-Typ

Architektur des Storage-Systems für virtuelle Maschinen.

Host-basierter Storage (Verteilter Storage):

  • Was ist das?
    • Jeder Host hat lokale Festplatten/SSDs
    • Software verbindet alle zu einem gemeinsamen Storage-Pool
    • VMs können auf allen Hosts gespeichert werden
  • Technologien:
    • VMware vSAN: Sehr beliebt, integriert in vSphere
    • Microsoft Storage Spaces Direct (S2D): In Windows Server
    • Nutanix HCI: Hardware + Software-Lösung
    • Ceph: Open Source, sehr flexibel
    • Proxmox Ceph: Ceph mit Proxmox-Integration
  • Vorteile:
    • Einfache Skalierung (neuer Host = mehr Storage)
    • Keine separate Storage-Hardware nötig
    • Oft günstiger als SAN
    • Hohe Performance mit SSDs/NVMe
  • Nachteile:
    • CPU/RAM der Hosts wird für Storage verwendet
    • Netzwerk-intensiv (Storage-Traffic zwischen Hosts)
    • Komplexere Konfiguration

Externer Storage (Zentrales Storage-System):

  • Was ist das?
    • Separates Storage-System (SAN/NAS)
    • Alle Hosts greifen darauf zu
    • Storage ist unabhängig von Hypervisor-Hosts
  • Technologien:
    • SAN (Fibre Channel): Sehr schnell, teuer, komplex
    • SAN (iSCSI): Über Ethernet, günstiger als FC
    • NAS (NFS/SMB): File-basiert, einfach
    • Object Storage: Für spezielle Anwendungen
  • Vorteile:
    • Hosts haben mehr CPU/RAM für VMs
    • Enterprise-Features (Dedupe, Compression, Snapshots)
    • Unabhängige Skalierung
    • Bewährte Technologie
  • Nachteile:
    • Hohe Anschaffungskosten
    • Separate Hardware = mehr Platz, Strom
    • Single Point of Failure (wenn nicht redundant)
    • Komplexe Verkabelung bei Fibre Channel

Wann welchen Typ?

  • Host-basiert: Moderne Umgebungen, wenn Hosts genug CPU/RAM haben, kleinere bis mittlere Installationen
  • Extern: Große Umgebungen, wenn bereits SAN vorhanden, wenn Storage-Features wichtig sind
Trend geht zu host-basiert (vSAN, HCI), aber externes Storage noch weit verbreitet!

Storage-Technologie

Wie ist das externe Storage-System angebunden?

Technologien erklärt:

  • SAN (Fibre Channel):
    • Dediziertes Fibre-Channel-Netzwerk
    • Sehr schnell (16/32 Gbit/s)
    • Block-basiert (LUNs)
    • Teuer, komplex
    • Gold-Standard für Mission-Critical
  • SAN (iSCSI):
    • SCSI über Standard-Ethernet
    • Günstiger als FC
    • 10 GbE empfohlen
    • Block-basiert
    • Guter Kompromiss Preis/Leistung
  • NAS (NFS/SMB):
    • File-basiert über Netzwerk
    • Einfach zu konfigurieren
    • NFS für VMware/Linux, SMB für Hyper-V
    • Etwas langsamer als SAN
    • Gut für nicht-kritische VMs
  • Object Storage:
    • S3-kompatibel
    • Für Backups, Archive
    • Nicht für Live-VMs
Wahl hängt ab von: Budget, Performance-Anforderungen, Expertise

Kapazität (TB)

Verfügbarer Storage-Platz auf dem externen System.

Was angeben:

  • Nutzbare Kapazität (nach RAID, Overhead)
  • Nicht die Roh-Kapazität!

Beispiel:

  • 10x 2TB Disks = 20 TB Roh-Kapazität
  • RAID 6 → 16 TB nutzbar
  • → Eintragen: 16 TB

Planung:

  • 80% Auslastung max. empfohlen
  • Snapshots brauchen extra Platz
  • VM-Wachstum einplanen
Lieber zu viel Storage als zu wenig - volles Storage = VMs können nicht starten!

Redundanz

Wie sind die Daten gegen Ausfall geschützt?

RAID-Level erklärt:

  • RAID 0 (Striping):
    • Keine Redundanz!
    • Höchste Performance
    • Eine Disk kaputt = alles weg
    • Nur für temp. Daten
  • RAID 1 (Mirroring):
    • Alle Daten doppelt gespeichert
    • 50% Kapazität nutzbar
    • Ein Disk-Ausfall OK
    • Einfach, aber teuer
  • RAID 5:
    • Daten + Parity verteilt
    • Ein Disk-Ausfall OK
    • ~75-80% Kapazität nutzbar (bei 4 Disks)
    • Standard für viele Jahre
    • ⚠️ Rebuild dauert lange bei großen Disks!
  • RAID 6:
    • Doppelte Parity
    • Zwei Disk-Ausfälle OK
    • ~66-70% Kapazität nutzbar
    • Empfohlen für große Storage-Systeme!
  • RAID 10 (1+0):
    • Mirroring + Striping
    • 50% Kapazität nutzbar
    • Sehr schnell
    • Mehrere Disk-Ausfälle möglich (kommt drauf an welche)
    • Beste Performance
  • Erasure Coding:
    • Moderne Alternative zu RAID
    • Flexibler (z.B. 8+3 = 8 Data + 3 Parity)
    • Besser für große Systeme
    • Ceph, vSAN nutzen das
  • Replikation:
    • Daten auf mehrere Storage-Systeme kopieren
    • Für Disaster Recovery
    • Synchron oder asynchron

Empfehlungen:

  • Performance: RAID 10 (teuer)
  • Kapazität: RAID 6 (sicher)
  • Budget: RAID 5 (aber nur mit kleinen Disks < 2TB)
RAID ist KEIN Backup! Redundanz schützt vor Hardware-Ausfall, nicht vor Fehlern/Viren!

Verfügbarer Speicherplatz für VMs in TB.

Planung:

  • File-Server: 2-10 TB

Gesamt CPU Cores

Die Summe aller physischen CPU-Kerne über alle Hosts.

Beispiel-Rechnung:

  • 3 Hosts à 2 CPUs mit je 16 Cores = 3 × 2 × 16 = 96 Cores gesamt

Warum wichtig:

Kapazitätsplanung - wie viele VMs können betrieben werden?

vCPU-Berechnung:

  • 96 physische Cores
  • Mit 4:1 Overcommitment = 384 vCPUs möglich
  • Typische VM hat 2-4 vCPUs
  • → Ca. 96-192 VMs möglich (abhängig von Last)
Mehr Cores = mehr VMs, aber beachte auch RAM und Storage als limitierende Faktoren!

Gesamt RAM (GB)

Die Summe aller physischen RAM über alle Hosts.

RAM ist meist der limitierende Faktor!

Nicht CPU - die meisten VMs sind RAM-limitiert, nicht CPU-limitiert.

Beispiel-Rechnung:

  • 3 Hosts à 512 GB RAM = 1536 GB total
  • Reserve für HA (20%): -307 GB
  • ESXi/Hyper-V Overhead (~5%): -77 GB
  • Verfügbar: ~1150 GB
  • Durchschnittliche VM: 8 GB
  • → Ca. 143 VMs möglich

Memory Overcommitment:

  • VMware/Hyper-V können mehr RAM vergeben als physisch vorhanden
  • Durch Memory Ballooning, Compression, Swap
  • Aber: Performance leidet erheblich!
  • Overcommitment bei RAM vermeiden - lieber mehr physischen RAM einbauen!
RAM-Engpässe führen zu Swapping = drastische Performance-Einbußen!

Gesamt Storage (TB)

Gesamter verfügbarer Storage für VMs.

Was zählt alles zum Storage:

  • VM-Festplatten (VMDKs/VHDXs)
  • Snapshots (können schnell mehrere TB belegen!)
  • VM-Templates und ISOs
  • Swap-Dateien
  • Log-Dateien

Thin vs Thick Provisioning:

  • Thin: Wächst dynamisch - 500 GB Disk belegt anfangs z.B. nur 50 GB
  • Thick (Lazy Zeroed): Platz sofort reserviert, aber nicht gelöscht
  • Thick (Eager Zeroed): Platz reserviert und sofort mit Nullen überschrieben (sicherer)

Planung:

  • Storage wächst schneller als erwartet
  • 20-30% Reserve für Snapshots einplanen
  • Monitoring für Storage-Kapazität einrichten
Voller Storage = keine neuen VMs, Snapshots können nicht erstellt werden!

Storage-Typ

Wie ist der Storage angebunden?

Storage-Typen erklärt:

  • Local Storage:
    • Festplatten direkt im Server
    • Schnell, günstig
    • Kein vMotion/Live Migration möglich!
    • Nur für Testumgebungen
  • SAN (Fibre Channel):
    • Dediziertes Storage-Netzwerk
    • Sehr schnell, sehr teuer
    • Enterprise-Standard
    • vMotion/HA möglich
  • iSCSI SAN:
    • SAN über Standard-Ethernet
    • Günstiger als Fibre Channel
    • Gute Performance bei 10G+ Netzwerk
    • Beliebt im Mittelstand
  • NFS:
    • File-basierter Storage
    • Einfach zu verwalten
    • Für VMware gut geeignet
  • vSAN / Software Defined:
    • Lokale Disks werden zu Cluster-Storage
    • Hyper-Converged Infrastructure (HCI)
    • Sehr flexibel, skalierbar
    • Modern, aber komplex
Shared Storage ist Voraussetzung für HA und vMotion!

Anzahl VMs (aktuell)

Wie viele VMs laufen derzeit auf dem Cluster?

Warum zählen:

  • Auslastung überwachen
  • Kapazitätsplanung (wann zusätzliche Hosts?)
  • Lizenzierung (oft pro VM)

VM-Density:

VMs pro Host - gibt Aufschluss über Auslastung

Overcommitment Ratio (CPU)

Wie viele vCPUs pro physischem Core?

Was ist CPU Overcommitment?

Mehr vCPUs vergeben als physische Cores vorhanden - funktioniert, weil VMs selten gleichzeitig 100% CPU nutzen.

Typische Ratios:

  • 1:1: Keine Überbuchung - sehr konservativ (Ressourcen-Verschwendung)
  • 4:1: Standard - funktioniert für die meisten Workloads gut
  • 8:1: Aggressiv - nur wenn VMs sehr idle sind (z.B. Development)
  • 10:1+: Zu viel - CPU-Warteschlangen und Performance-Probleme!

Beispiel-Rechnung:

  • 96 physische Cores
  • 4:1 Ratio
  • = 384 vCPUs können vergeben werden
  • Bei 192 VMs à 2 vCPUs = 384 vCPUs belegt

Workload-abhängig:

  • CPU-intensive VMs (Datenbanken, Rendering): 2:1 bis 3:1
  • Standard-Server (Webserver, Fileserver): 4:1 bis 6:1
  • Idle VMs (Development, Test): 8:1 bis 10:1
4:1 ist sicher für gemischte Workloads, 8:1 funktioniert oft, mehr ist riskant

Management Netzwerk

Das Netzwerk für Hypervisor-Management.

Was läuft über Management:

  • ESXi/Hyper-V Web-UI Zugriff
  • vCenter ↔ ESXi Kommunikation
  • SSH/PowerShell-Zugriff

Best Practices:

  • Dediziertes VLAN (z.B. VLAN 10)
  • Nur aus Admin-Netz erreichbar
  • Redundante Netzwerkkarten

Beispiel:

"192.168.10.0/24, VLAN 10"

vMotion / Live Migration Netzwerk

Das Netzwerk für Live-Migration von VMs zwischen Hosts.

Was ist vMotion/Live Migration?

VM ohne Downtime von einem Host zu anderem verschieben - der komplette RAM-Inhalt wird übertragen!

Warum separates Netzwerk:

  • Sehr bandbreiten-intensiv (10+ GB RAM-Transfer pro VM)
  • Sollte Produktiv-Netzwerk nicht belasten
  • Latenz-sensitiv - langsames Netzwerk = lange Migration
  • Dediziertes 10G+ Netzwerk dringend empfohlen

Best Practices:

  • Minimum 10G, besser 25G oder 40G
  • Dediziertes VLAN
  • Redundante NICs (NIC Teaming)
  • Jumbo Frames (MTU 9000) aktivieren

Beispiel:

"192.168.20.0/24, VLAN 20, 10G Ethernet"
Langsames vMotion-Netzwerk = Migration dauert Minuten statt Sekunden!

Storage Netzwerk

Das Netzwerk für Storage-Kommunikation (iSCSI, NFS).

Warum separates Storage-Netz:

  • Alle VM-Disk-Zugriffe laufen darüber
  • Sehr hoher Traffic
  • Latenz-kritisch
  • Sollte isoliert sein

Best Practices:

  • Minimum 10G, besser 25G+
  • Redundante Pfade (Multipathing)
  • Dediziertes VLAN
  • Jumbo Frames aktiviert (MTU 9000)

Beispiel:

"192.168.30.0/24, VLAN 30, 25G"

VM Netzwerke / Port Groups

Die Netzwerke, die VMs nutzen können.

Was sind Port Groups?

Virtuelle Netzwerk-Segmente für VMs - wie VLANs.

Typische VM-Netzwerke:

  • Prod-VLAN100 - Produktiv-Server
  • DMZ-VLAN200 - DMZ-Zone
  • Backup-VLAN300 - Backup-Netzwerk
  • Test-VLAN400 - Test-VMs

Sicherheit:

VMs sollten in verschiedenen VLANs sein je nach Funktion (Segmentierung)

Distributed Switch / Virtual Switch

Der virtuelle Switch für Netzwerk-Konfiguration.

Standard vs Distributed Switch:

  • Standard vSwitch: Pro Host konfiguriert - einfach, aber viel Arbeit bei vielen Hosts
  • Distributed vSwitch (vDS): Zentral über vCenter - konsistente Konfiguration über alle Hosts

Beispiel:

"vDS-Production" oder "vSwitch0"
Distributed Switch ist Pflicht für größere Umgebungen!

Physische NICs / Uplinks

Die physischen Netzwerkkarten (Network Interface Cards) im Server.

Typische Konfigurationen:

  • 2x 1 GbE: Minimum für kleine Umgebungen
  • 4x 10 GbE: Standard für Produktion
  • 2x 25 GbE: Modern, gut für Storage + vMotion
  • 2x 40/100 GbE: High-End für große Umgebungen

Best Practices:

  • Mindestens 2 NICs pro Netzwerk (Redundanz)
  • Separate NICs für Management, vMotion, Storage, VMs
  • 10 GbE Minimum für Storage-Netzwerk
  • Link Aggregation (LACP) für höhere Bandbreite

Typisches Setup (4 NICs):

  • NIC 1+2: Management + vMotion (Team/Bond)
  • NIC 3+4: VM Networks (Team/Bond)

Großes Setup (6+ NICs):

  • NIC 1+2: Management (redundant)
  • NIC 3+4: vMotion (redundant)
  • NIC 5+6: Storage (redundant)
  • NIC 7+8: VM Networks (redundant)
Mehr NICs = bessere Performance + Redundanz, aber auch höhere Kosten!

Management-Tool

Die Software zur Verwaltung des Hypervisors.

Tools erklärt:

  • vCenter: VMware zentrale Management-Plattform (für Cluster)
  • System Center VMM: Microsoft für Hyper-V (Enterprise)
  • Proxmox Web UI: Eingebaut in Proxmox
  • Xen Orchestra: Web-UI für XenServer/XCP-ng
  • virsh / virt-manager: Kommandozeile / GUI für KVM

Ohne Management-Tool:

Jeder Host einzeln verwalten = Alptraum!

Monitoring / Alerting

Wie wird der Hypervisor überwacht?

Was überwachen:

  • Host-Status (Up/Down)
  • CPU/RAM-Auslastung pro Host
  • Storage-Kapazität und Performance
  • VM-Status
  • HA-Events
  • Datastore-Latenzen

Monitoring-Tools:

  • vROps (VMware vRealize Operations) - Premium
  • PRTG - Windows-fokussiert
  • Zabbix - Open Source
  • Nagios/Icinga - Open Source
Hypervisor-Ausfall = viele VMs down - Monitoring ist kritisch!

Backup-Lösung

Welche Software sichert die VMs?

VM-Backup-Lösungen:

  • Veeam: Marktführer, sehr gut für VMware/Hyper-V
  • Altaro: Günstiger, für KMU
  • Commvault: Enterprise, teuer
  • Nakivo: Alternative zu Veeam
  • Proxmox Backup Server: Für Proxmox

Agentless Backup:

Backup direkt auf Hypervisor-Ebene (ohne Agent in VM) - einfacher!
VM-Backup ist essentiell - Snapshots sind KEIN Backup!

Lizenzmodell

Wie wird der Hypervisor lizenziert?

Lizenzmodelle erklärt:

  • Perpetual (Unbefristet): Einmalkauf, Updates oft extra - VMware früher, jetzt deprecated
  • Subscription (Abonnement): Jährliche Zahlung - VMware seit 2024, Microsoft
  • Per CPU/Socket: Pro physischem CPU-Sockel - VMware vSphere
  • Per Core: Pro CPU-Core - Microsoft Hyper-V (über Windows Server Core Lizenzen)
  • Per VM: Pro virtueller Maschine - selten, einige Cloud-Provider
  • Free/Open Source: ESXi Free (limitiert), Proxmox (Community), KVM

VMware-Beispiel:

  • vSphere Standard = 3 Hosts à 2 CPUs = 6 CPU-Lizenzen nötig
  • Subscription: ~6.000-8.000 EUR/Jahr pro CPU

Microsoft-Beispiel:

  • Windows Server 2022 Datacenter = pro 16 Cores (min. 2 Lizenzen à 16 Cores pro Server)
  • Datacenter = unbegrenzte VMs
Lizenzkosten können sehr hoch sein (mehrere 10.000 EUR/Jahr) - gut planen und vergleichen!

Support-Level

Welchen Support-Vertrag haben Sie?

Support-Level:

  • Production Support (24/7): Anruf jederzeit, kritisch für Produktiv
  • Business Support (5x8): Mo-Fr Bürozeiten
  • Basic Support: E-Mail, langsame Response
  • Community Support: Nur Community-Foren
  • Kein Support: ESXi Free, keine Hilfe vom Hersteller
Bei kritischen Clustern: 24/7 Support ist Pflicht!
